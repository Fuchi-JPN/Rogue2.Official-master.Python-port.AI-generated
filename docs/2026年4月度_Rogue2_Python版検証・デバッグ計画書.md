## 2. 検証の目的と方針

### 2.1 目的

C言語版Rogue2.OfficialとPython移植版が**コンソール画面上で同じ動作を実現できているか**を、ゼロベースで体系的に検証する。

### 2.2 方針

1. **前提を置かない検証**: 過去の修正履歴や報告書を参照はするが、それを正とせず全項目を再検証する
2. **C言語版を唯一の正**: 全ての判定基準はC言語版ソースコード(`src/`)とする
3. **画面出力が最終判定**: 内部ロジックの正確性に加え、コンソール上の表示がC版と一致することを最終目標とする
4. **段階的検証**: 下層（定数・データ構造）→中層（ロジック）→上層（統合動作）の順に検証し、下層の不具合は上層の検証前に修正する

## 4. 検証計画

### 4.1 検証フェーズ構成

```
フェーズ0: 前提確認（定数・データ構造の完全一致検証）
    ↓
フェーズ1: 単体ロジック検証（関数レベルの入出力一致検証）
    ↓
フェーズ2: 状態管理検証（グローバル変数・状態遷移の一致検証）
    ↓
フェーズ3: 統合動作検証（ゲームプレイシナリオベースの一致検証）
    ↓
フェーズ4: 画面出力検証（コンソール表示の完全一致検証）
```

## 5. 検証実施方法

### 5.1 自動比較スクリプトの作成

フェーズ0～1の定数・データ構造・関数レベルの検証を自動化するため、以下のスクリプトを作成する。

| スクリプト名 | 目的 | 入力 | 出力 |
|-------------|------|------|------|
| `verify_constants.py` | C版#defineとPython版定数の自動比較 | rogue.h, const.py | 差分一覧 |
| `verify_structs.py` | C版structとPython版classのフィールド比較 | rogue.h, entities.py | 過不足一覧 |
| `verify_mon_tab.py` | mon_tab[26]の全フィールド値比較 | monster.c, entities.py | 差分一覧 |
| `verify_messages.py` | メッセージリソースの網羅性・本文比較 | mesg_J, text_resources.py | 差分一覧 |
| `verify_function_map.py` | C版関数とPython版メソッドの対応表作成 | 全ソース | 対応表・未実装一覧 |

### 5.2 比較実行環境の構築

C言語版とPython版を同一シードで実行し、出力を比較する環境を構築する。

1. **C版の改造**: デバッグ出力用に、各関数の入出力をログ出力する版をビルド
2. **Python版の改造**: 同様にログ出力するモードを追加
3. **比較方法**: 同一シード・同一入力シーケンスで実行し、ログをdiff比較

### 5.3 テスト駆動の修正サイクル

```
1. 検証項目の実施 → 不具合の発見
2. 不具合の記録（検証ID、期待値、実際値、原因分析）
3. 修正の実施
4. 修正の検証（当該検証項目の再実行 + 回帰テスト）
5. 次の検証項目へ
```

## 7. リスクと対策

| リスク | 影響度 | 対策 |
|--------|--------|------|
| 乱数の非決定性 | 高 | シード固定テストを前提とする。Python版はrandomモジュール、C版は自前RNGのため、同一シードでも同じ乱数列にはならない。シード固定時のマップ生成結果の完全一致は期待せず、ロジックの正確性で判定する |
| 3重管理の修正が大規模変更になる | 高 | game_state.pyへの集約を段階的に実施。まず読み取りを集約し、次に書き込みを集約する |
| C版の条件コンパイル(#if ORIGINAL) | 中 | ターゲットを非ORIGINAL版（日本語版）に限定し、ORIGINAL版の差分は低優先とする |
| cursesのプラットフォーム差異 | 低 | 検証はUbuntu Linux上で実施する |
| テキストエンコーディング差異 | 低 | Python版はUTF-8、C版はEUC-JP/Shift-JIS。text_resources.pyで既に変換済みのため、表示結果で判定する |
