# rougeclone2 AI自律プレイエージェント — 企画書・詳細仕様書

## 概要

本書は、AIエージェントのみでPython移植を進めている rougeclone2（データ分離版ローグ・クローンII UTF-8版）について、その未完成の本体（以下「本体」）に極力手を加えることなく、外部からAIエージェントが全操作を行えるようにするための企画と詳細仕様をまとめたものである。プレイヤー側AI（自律プレイエージェント）の開発・デバッグと、本体側の間接的なデバッグという2つの目的を同時に達成することを狙う。

## 第I部　企画書

### 1. 背景

- rougeclone2（データ分離版ローグ・クローンII UTF-8版）をAIエージェントのみでPythonに移植する取り組みを進行中だが、デバッグが難航しており、完成と呼べる水準には至っていない。
- rougeclone2の元となったC言語版は、curses/termcapによる画面制御、hjkl等のvi系キー操作、1〜2文字コマンド体系という明確な仕様を持つ古典的なローグライクである（詳細は8章）。仕様自体は明確だが、ダンジョン生成・モンスターAI・アイテム識別・空腹管理など状態の組み合わせが多く、人手による網羅的なデバッグには限界がある。
- 一方で、このゲームはコマンド体系がシンプルかつ有限であり、画面出力もテキストベースであるため、AIエージェントに「プレイさせる」ことで大量かつ多様な操作パターンを機械的に本体へ流し込む土台として適している。

### 2. 目的

本企画は、次の2つを同時に達成することを目的とする。

1. **プレイヤー側AI（自律プレイエージェント）の開発・デバッグ**：実際に動作する具体的な対象（rougeclone2）を持つことで、状態認識・意思決定・長期的なゴール管理（飢餓の管理、未識別アイテムの扱い、下降を続けるか撤退するかの判断等）を伴うAIエージェントの実装・改良を進める。
2. **本体（rougeclone2 Python移植版）の間接的なデバッグ**：1.のエージェントに本体を自律的かつ長時間・大量にプレイさせることで、人手のプレイテストでは気づきにくいクラッシュ・状態不整合・表示崩れ等を検出する。

### 3. 期待される効果

- 本体のソースコードを変更せずに、繰り返し実行できる自動プレイ／擬似回帰テストの仕組みが得られる。
- エージェントが残す操作ログ・画面ログ・判断根拠が、本体デバッグ時の一次資料として活用できる。
- プレイヤーAI自体も、状態空間が広く不確実性の高い（アイテムの効果が毎回ランダムに変わる等）環境でどこまで合理的に振る舞えるかという、それ自体独立した技術的テーマになる。

### 4. スコープ

- 本体を無改変の外部プロセスとして起動し、擬似端末（PTY）経由で全操作をキーストロークとして送信し、画面出力を取得・解析することで、AIエージェントからの完全な操作を可能にするハーネス（以下「本ハーネス」）一式。
- 本ハーネス上で動作するプレイヤーAI：スモークテスト用の最小実装（ルールベース）と、本命であるLLMベースの実装。
- ロギング・リプレイ・クラッシュ検知・状態差分チェックなど、デバッグを支援する周辺機能。

### 5. 非スコープ（対象外とすること）

- 本体のロジック修正・バグ修正そのもの。本企画の役割はあくまで「不具合の発見」までであり、「修正」は別タスクとして扱う。
- 勝率・攻略効率を最大化する高性能なRogue攻略AIを作ること自体を主目的とはしない（副次的な成果としてはあり得るが、優先度は低い）。
- 端末エミュレーションの自前実装。既存のライブラリ資産（後述）を優先的に活用する。
- 複数セッションの並列実行など、運用の高度化。まずは単一セッションを安定して動かせることを優先する。

### 6. 成功基準

- 本ハーネス経由で本体を、ハーネス起因の異常を発生させることなく一定ターン数以上動作させ続けられる（本体側のクラッシュ自体は想定内であり、検知・記録できていれば良い）。
- 画面パーサーが自機座標・HP・メッセージ内容を、目視照合による検証で十分な精度で抽出できる。
- ルールベースの最小プレイヤーで「移動→アイテム取得→階段を降りる」という基本ループが最後まで閉じることを確認できる。
- 蓄積したログから、人手のプレイテストでは気づきにくい本体側の不具合を最低1件以上、具体的に特定できる。

### 7. リスクと対応方針

| リスク | 対応方針 |
|---|---|
| 本体が未完成のため頻繁にクラッシュ・ハングする | ハーネス側はクラッシュ・無応答を前提とし、検知・記録・再起動を標準機能として組み込む |
| 画面のASCIIアート解析は本質的に壊れやすい | Phase 0でのキャリブレーションを必須工程とし、想定外フォーマットはクラッシュではなくログ＋フォールバックで受け止める |
| UTF-8全角文字混在によりカラム計算がずれる | 端末エミュレーション層で全角文字幅を明示的に考慮し、Phase 0で実画面に対して検証する |
| LLMエージェントのプロンプトが長時間プレイで肥大化する | 直近履歴のみ保持し、それ以前は要約するスライディングウィンドウ設計とする |
| 想定した原典仕様と実際のPython移植版の挙動が食い違う | 本仕様内の原典由来の記述はすべて「要検証」として明示し、Phase 0で実機確認後に更新する（16章） |

## 第II部　詳細仕様書

### 8. 前提の整理 — rougeclone2の仕様概観

以下は、公開されている「データ分離版ローグ・クローンII」系統（伊藤康史氏原作、太田純氏の日本語版を起点とし、FUNABARA Masao氏・Naohiro Aota氏・鈴木維一郎氏による継承版に至る、curses/termcapベースのC言語プログラム）の公開ドキュメントに基づく一般的な整理である。**対象のPython移植版が同じ挙動を持つ保証はなく、差異があり得る前提で読むこと**（差異の確認方法は16章）。

- **起動方法**：`./rogue <メッセージファイル名>` の形で起動し、メッセージファイルをコマンドライン引数として与える必要がある（データ分離の設計のため）。第2引数以降でスコア表示オプションやセーブファイル名を指定できる。
- **画面サイズ**：最小80桁×24行を前提とする。
- **画面構成**：最上行がメッセージ表示専用、最下行がステータス表示専用、その間がダンジョンマップ。
- **ステータス行**：階数／所持金／HP（現在値・最大値）／強さ（現在値・最大値）／防御力／経験（レベル・経験値）を表示し、空腹時には状態表示（「空腹」「飢餓」相当）が追加される。
- **メッセージ行の「続き」表示**：表示しきれないメッセージがある場合、続きを読むためのキー入力待ち状態になる。この待ち状態を示す具体的な文字列は、データ分離の設計上メッセージファイルに依存するため、原典の英語表記（"--More--"）をそのまま前提にできない（13章・16章で後述）。
- **操作体系**：hjkl（大文字で衝突するまで継続移動）とyubn（斜め移動）を基本とし、その他1〜2文字のコマンドで持ち物操作・戦闘・階段昇降等を行う古典的な体系（付録A）。
- **マップ上のシンボル**：`@`（自機）、`-`/`|`（壁）、`+`（ドア）、`.`（部屋の床）、`#`（通路）、`*`（金塊）、`)`（武器）、`]`（防具）、`!`（薬）、`?`（巻物）、`=`（指輪）、`/`（杖）、`^`（罠、通常は隠れている）、`%`（階段）、`:`（食料）、`A`〜`Z`（モンスター）が用いられる（付録B）。
- **アイテム識別**：巻物・薬はゲームごとにランダムなラベルが振られ、1度使用するとその回のプレイ中は効果が判明する。
- **セーブ**：セーブ→終了のコマンドがあり、原典の設計では再開時にセーブファイルが消費される（セーブスカム防止のため）。

### 9. 全体アーキテクチャ

本体を一切改変せず、外部プロセスとして扱うレイヤー構成とする。

```
L5  エージェントコア（Policy）           状態から行動を決定する
L4  アクション変換層／リフレックス層     行動⇄キーストローク変換、機械的応答の自動処理
L3  画面パーサー／状態抽出層             画面 → 構造化状態(GameState)
L2  端末エミュレーション層               raw出力 → 画面バッファ再構成
L1  プロセス制御層（PTY／tmux）          プロセス起動・入出力の橋渡し
L0  rougeclone2 本体（無改変）           対象システム（外部プロセス）

L6  セッション管理・ロギング層 は上記全層を横断し、
    各層の入出力・判断・例外をすべて記録する
```

各ターンは L5→L4→(L1経由で入力送信)→L0→L1→L2→L3→L5 という順に処理が一巡する。

実装・運用方針は既存の個人開発方針を踏襲し、標準venv＋pipで完結させ、Docker等の追加インフラは導入しない。常時稼働のデーモンではなく、プレイセッション単位で起動・終了するスクリプトとして実装する。

### 10. レイヤー別詳細設計

#### 10.1 プロセス制御層

本体プロセスの起動・入出力を担う層。2つの実装案を比較する。

| | 案A: tmux + libtmux（推奨） | 案B: PTY(os.openpty) + ptyprocess + pyte |
|---|---|---|
| 概要 | tmuxのセッション内で本体を起動し、send-keysで入力、capture-paneで画面取得 | 自前でPTYを開き、pyteで端末エミュレーションして画面バッファを再構成 |
| 利点 | 実績ある端末エミュレーションをそのまま利用できる。tmux attachで人間が同一セッションをリアルタイム観察でき、デバッグ目的（目的2）に直結する。実装量が少ない | 外部プロセス非依存の純Python。セル単位の色・属性への低レベルアクセスが可能。ユニットテストがしやすい |
| 欠点 | tmuxという外部プロセスへの依存が増える。色・属性の取得にはcapture-paneのオプション調整が必要 | 実装・保守コストが高い。リサイズや初期化シーケンスを自前で正しく扱う必要がある |
| 個人開発方針との整合性 | bare-metal寄り・オーバーエンジニアリング回避の方針に合致 | 依存を減らせる点は合致するが実装コストが方針（低コスト・省リソース優先）とややトレードオフ |

**推奨**：まず案Aで実装し、色・属性情報が本当に必要になった場合にのみ案Bへの切替・併用を検討する。

具体実装によらない共通インターフェースを次のように定義し、L2以降は実装の詳細を意識しなくてよいようにする。

```python
class GameProcessController:
    def start(self, argv: list[str], cols: int = 80, rows: int = 24) -> None: ...
    def send_keys(self, data: str) -> None: ...
    def capture_screen(self) -> str: ...   # 現在の画面をプレーンテキストで取得
    def is_alive(self) -> bool: ...
    def exit_code(self) -> int | None: ...
    def restart(self) -> None: ...
```

起動コマンド（例：["./rogue", "<メッセージファイル名>"]）と画面サイズ（80×24固定）は設定値として外出しし、Phase 0で確定させる。

#### 10.2 端末エミュレーション層

- 案A（tmux）採用時：この層はtmux自体が担うため薄いラッパーで足り、capture-paneの出力をパースしやすい形（行配列）に整形する程度でよい。
- 案B（pty+pyte）採用時：pyte.Screen + pyte.Stream にバイト列を流し込み、Screen.display から行配列を得る。
- どちらの案でも、日本語メッセージ・アイテム名に含まれる全角文字の幅（East Asian Width）を正しく扱えているかをPhase 0で検証する。マップ本体のシンボルは半角記号のみと想定されるが、メッセージ行・持ち物名は全角混じりになるため、カラムずれのリスクが高い箇所として重点的に確認する。

#### 10.3 画面パーサー／状態抽出層

- **入力**：80×24のプレーンテキスト画面（1フレーム分）。
- **出力**：後述の GameState（11章）。
- **責務**：
  - マップ領域から、自機座標・壁/床/通路の配置・視認できるモンスターとアイテムを抽出する。
  - ステータス行（最終行）から階数・所持金・HP・強さ・防御力・経験・空腹状態を抽出する。
  - メッセージ行（最上行）からメッセージ文字列を取り出し、「続き」待ち・y/n確認・方向入力待ち・持ち物選択待ちなどの特殊状態を判定する。
  - インベントリ一覧・ヘルプ・オプション・死亡/スコア画面など、通常のダンジョンビューでない全画面モードを検出する。
- **設計方針**：想定外のフォーマットに遭遇した場合は例外を送出してプロセス全体を止めるのではなく、mode="unknown" として記録した上で安全側の選択肢のみをL4・L5に提示する。パーサーの誤りが即座に全体停止に繋がらないようにする。

#### 10.4 アクション変換層とリフレックス層

- エージェント（L5）が選択するのは「意味のある行動」（例：{"type": "move", "direction": "north"}）であり、実際の1〜2文字のキーストロークへの変換はこの層に集約する。実際のキー割当がPhase 0確認により原典と異なると判明した場合も、修正箇所をこの層に限定できる。
- **リフレックス層**：エージェントの判断を介さず機械的に処理すべき画面状態（例：メッセージの「続き」待ち）を自動的に処理し、継続キーを送信する。一方、y/n確認・方向選択・持ち物選択のように、ゲーム進行上の意味を持つ選択はすべてL5（エージェント）の判断対象として渡す。
- アクション⇄キーストロークの対応表は付録Aを土台とする。

#### 10.5 エージェントコア（プレイヤーAI）

行動決定ロジックを差し替え可能にするため、ポリシーインターフェースとして抽象化する。

```python
class Policy:
    def decide(self, state: GameState, history: list[Turn]) -> Action: ...
```

実装候補：

- **ScriptedPolicy（最小実装）**：ランダム移動＋障害物回避程度のルールベース実装。Phase 1〜4でのハーネス自体の動作検証・スモークテストに用いる。
- **LLMPolicy（本命）**：GameState をプロンプト化し、ツール呼び出し形式で行動を選ばせ、結果を Action に変換する。

LLM呼び出しのバックエンドは、既存のローカルLLM環境や外部APIをそのまま利用できるよう、OpenAI互換API形式のクライアント抽象を介して行い、設定で切替可能にする。将来的には、コスト最適化のために既存のコスト振り分け基盤と同様のロジックを流用・共有することも選択肢になりうる。

コンテキスト管理として、1ターンあたりの状態（80×24画面）自体はコンパクトだが、メッセージ履歴・行動履歴は長時間プレイで肥大化するため、直近Nターンのみを保持し、それ以前は要約する設計とする。また、アイテムのラベルと効果の対応はゲームごとにランダムに変わるという本ゲーム特有の性質があるため、エージェントが対局内で学習した対応関係を保持する「識別メモ」を状態の一部として持たせる。

#### 10.6 セッション管理・ロギング層

- **記録対象**：生の画面出力（またはraw出力バイト列）、送信した入力、パース後の構造化状態、選択された行動、（LLM使用時は）判断根拠、例外・クラッシュ情報。
- **クラッシュ検知**：プロセスの異常終了、または一定時間画面に変化がない状態（ハング）を検知し、直前N画面・直前入力・終了コードを保存したうえでセッションを再起動する。
- **リプレイ**：記録した生ログを後から端末エミュレーション層に再投入することで、本体を再実行せずに事後解析できるようにする。

### 11. データスキーマ

```python
@dataclass
class StatusLine:
    level: int | None
    gold: int | None
    hp_cur: int | None
    hp_max: int | None
    str_cur: int | None
    str_max: int | None
    armor: int | None
    exp_level: int | None
    exp_points: int | None
    hunger: Literal["normal", "hungry", "weak", "starving"] | None

@dataclass
class GameState:
    turn: int
    raw_screen: list[str]                    # 24行×80桁の生テキスト
    player_pos: tuple[int, int] | None
    map_tiles: dict[tuple[int, int], str]    # 座標 -> シンボル
    visible_monsters: list[dict]             # [{"pos": (x, y), "symbol": "K"}, ...]
    visible_items: list[dict]                # [{"pos": (x, y), "symbol": "!"}, ...]
    status: StatusLine | None
    message: str | None
    mode: Literal[
        "normal", "more_prompt", "yn_prompt", "direction_prompt",
        "item_select", "inventory_view", "help_view", "dead", "unknown",
    ]

@dataclass
class Action:
    type: str                     # "move" | "quaff" | "read" | "wield" | ...
    direction: str | None = None
    item_slot: str | None = None
    raw_keys: str | None = None   # 上記で表現しきれない操作用のエスケープハッチ
```

raw_keys は、意味づけされた行動モデルでカバーしきれない操作が判明した場合の直接キー指定用の逃げ道として用意する。

### 12. 主要シーケンス

- **起動**：プロセス起動 → 初期画面が安定するまで数フレーム分ポーリング → 初期状態を抽出。
- **通常ターン**：状態取得 → パース → modeが more_prompt 等ならリフレックス層が自動処理 → それ以外はL5（エージェント）へ渡す → 行動決定 → キーストローク送信 → 次状態取得。
- **異常系**：プロセス死亡・ハング検知 → 直前ログを確定・保存 → セッション再起動 → 新規ダンジョンから再開（セーブ再開の扱いは13章参照）。
- **終了**：死亡画面・目的達成・規定ターン数到達のいずれかで正常終了し、ログ一式を保存する。

### 13. rougeclone2固有の考慮事項

- **全角文字幅の扱い**：マップ本体は半角記号のみのはずだが、メッセージ・持ち物名には日本語（全角）が含まれるため、画面上のカラム位置とパーサーの列インデックスがずれるリスクがある。端末エミュレーション層の設定と、実画面でのパディング挙動をPhase 0で確認する。
- **「続き」待ち文字列の非英語化**：原典は英語版で"--More--"だが、データ分離版ではメッセージファイル由来の文字列である可能性が高く、ハードコードすべきではない。実機画面から実際の文字列を確認し、設定値として外出しする。
- **メッセージ資源ファイルの読み取り活用（改変ではなく参照）**：本系統は伝統的に「メッセージ番号→文字列」形式の外部データファイルでUIテキストを管理してきた。Python移植版が同様の資源ファイル（テキストファイルやPython辞書等）を保持しているなら、それを変更せずに読み取ることで、パーサーの照合パターンを実際の文言から機械的に導出できる可能性がある。実装時に確認する価値がある。
- **アイテム識別の即時確定**：本系統では巻物・薬は1度使用すれば効果が判明する仕様のため、識別メモ機構も複数回試行を前提としない単純な設計でよい。
- **セーブ・再開の扱い**：原典のセーブは一度きりの再開用という特殊な仕様であり、Python移植版での対応状況は不明である。当面は「1セッション＝1ダンジョン、プロセス生存中は継続」を基本方針とし、セーブ対応の要否はPhase 0の確認結果を踏まえて判断する。

---

### 14. テスト・デバッグ支援機能

- **画面ダンプビューア**：任意ターンの生画面とパース結果を並べて確認できる簡易スクリプト。
- **状態差分チェッカー**：送信した行動と実際の状態遷移を突き合わせ、想定外の結果（例：移動を送ったのに座標が変わらず、障害物も検出されていない）を異常候補としてログに記録する。
- **決定的リプレイ**：既知の不具合を再現する入力列を記録・再送できる仕組み。
- **ヘッドレス・スモークテスト**：ScriptedPolicy により無人でNターン実行し、ハーネスと本体の組み合わせが安定して動作するかを確認する回帰テスト用途。
